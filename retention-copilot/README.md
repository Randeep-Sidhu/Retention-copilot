# Retention Copilot

Agentic churn-to-action system: a calibrated churn model finds at-risk customers, a LangGraph agent drafts a
policy-compliant retention action for each one, a deterministic verifier checks it, and a human approves it.

> Work in progress. Done: data/model/business case (phase 1), policy corpus + retriever + deterministic verifier (phase 2),
> LangGraph agent + evaluation harness (phases 3-4). Next: Streamlit review app and write-up. Everything below is generated by code; see `reports/model_card.md` for current results.

## Quickstart (Phase 1)

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate      macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
python -m src.phase1     # downloads IBM's public Telco sample, trains, audits, writes db/, artifacts/, reports/
pytest -q                # offline tests (no network, no LLM)
python -m src.retrieval_eval   # TF-IDF vs dense vs hybrid retrieval on 28 gold queries
```

Requires Python 3.11+ (3.12 recommended).

## What Phase 1 produces
- `db/retention.db` - SQLite: `customers`, `scores`, `labels`, `audit_attributes`, and the only agent-visible
  view `v_customer_profile` (no label, no demographics).
- `artifacts/model.joblib` - fitted model and explainer.
- `reports/model_card.md`, `reports/metrics.json`, `reports/figures/*.png`.

## Phase 2: policy corpus and verifier
- `src/policy_spec.py` is the single source of truth for the (fictional) retention policy. `python -m src.policy_docs`
  renders `policies/*.md` from it, and `src/policy_engine.py` enforces the same constants, so the text the LLM
  retrieves and the rules that check its output cannot drift apart (a test fails if they do).
- `src/retriever.py`: section-level chunks; TF-IDF, dense (fastembed) or hybrid retrieval.
- `src/policy_engine.py`: eligibility, terms, preferred offer, and `check()` which returns actionable violations.
- `src/reference_drafter.py`: a deterministic policy-perfect drafter. A property test shows it passes the verifier
  for 1,500 random customers, i.e. the policy is satisfiable and internally consistent.

## Phase 3-4: agent and evaluation
```
load_customer (read-only SQL) -> gate (expected value) -> policy context (none | full | multi-hop RAG)
   -> draft (Granite via Ollama, schema-constrained JSON) -> verify (deterministic policy engine)
   -> [revise with violation feedback]* -> finalize (run log + human review queue)
```
- `src/sql_tool.py`: the agent can only `SELECT` from one view; enforced by a SQLite authorizer, not by the prompt.
- `src/agent.py`: LangGraph state machine with branching, a bounded repair loop and escalation to a human.
- `src/evaluate.py`: 6 configurations (policy source x verifier loop) on 48 held-out customers; paired exact tests.
  Run on a free GPU with `notebooks/kaggle_agent_eval.ipynb`; results land in `reports/agent_eval.md`.

## Data note
IBM's public Telco churn sample. Two fields (`marketing_opt_in`, `contacts_last_90d`) are **simulated** so that
compliance rules can be tested; they are never model inputs. Business-value figures rest on stated assumptions
(no offer/no-offer experiment exists in the data).
